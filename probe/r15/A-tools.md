# Tester A: tool calls + asynchrony, 1.0 (`higgs-realtime`) vs 1.5 (`higgs-realtime-1.5-preview`). Oct 23. Script: a_tools.py, raw events: A-tools.jsonl
Setup per run: text mode, TOOL_DEF + PROMPT+MECHANICS from higgslive.py, user asks "make groceries.txt"; then bare ack, 2 unrelated turns, output at 30 s, bare response.create, recall question.

- Q5 (GET /v1/models): 1.5 entry has the same fields as 1.0 (owned_by vllm, metadata null, max_model_len 32768). Nothing new on it. New models listed: higgs-realtime-tts, higgs-tts-mps, qwen3-forced-aligner-0.6b, higgs-avatar.
- session.created on 1.5 echoes our tools/instructions/tool_choice (it already contains the first session.update); key set identical to 1.0. Still no session.updated on 1.5.
- `usage` is NO LONGER null on either model (contradicts INDEX gotcha): input/output/total tokens + cached_tokens. Same prompt = 608 input tokens on 1.5 vs 486 on 1.0 (1.5 renders tools/system ~120 tokens bigger).
- TOOL CALL RATE, first turn: 1.0 called delegate_task 4/4. 1.5 called 2/5; the other 3/5 it said "I've handed that off to an agent..." with NO call (fake claim, text only). Biggest risk found. (N small; phase 2 fake-claim rate.)
- 1.5 speaks a preamble in the SAME response as the call ("I'll get that file set up for you right away.") 2/2; 1.0 call responses carry empty text 4/4.
- 1.0 over-calls: 2/4 runs emitted extra parallel delegate_task calls ("verify the file", "check its size"; up to 4 in one response), and 1/4 re-called in the bare-ack response. 1.5: exactly 1 call 2/2, no re-call.
- Q1 open call across unrelated turns: 1.0 4/4 and 1.5 2/2: no error, no re-call during the 2 unrelated turns. Extra 1.0 calls we never answered stayed open for the whole session, no error either.
- Q2 bare response.create after the call: natural ack, no re-greeting, 1.0 3/4 (4th was the re-call), 1.5 2/2 ("I've handed that off ... What else can I help you with while it's being set up?").
- Q3 output 30 s / 2 turns later: incorporated in the next bare response and recalled verbatim on a later turn, 1.0 4/4, 1.5 2/2. function_call_output acked with conversation.item.added on both.
- 1.5 is task-aware in unrelated turns: 1/2 runs appended "...while the grocery list file is being created!" to the Canberra and joke answers. 1.0 never did.
- call_id format differs: 1.0 `chatcmpl-tool-<32 hex>`, 1.5 `chatcmpl-tool-<16 hex>` (different serving/parser stack).
- Latency (text mode, send → response.done): 1.0 0.15-0.55 s, 1.5 0.35-1.8 s (ack/turns ~1.5 s typical). 1.5 is ~3x slower in text.
- Q4 `delegate` on 1.5 (N=1 per schema, same on 1.0 N=1): still hijacked, executor:"server", output still "The delegation service is not configured." ~0 ms after the call (instant stub). No background model reachable. 1.5 then answers itself ("isn't available, so I'll give you my best thinking directly"), 1.3-2 s later.
- The server tool is a Python function: if our schema has `task`, the output is "Error: _delegate() got an unexpected keyword argument 'task'" (same for web_search with `query`: "_web_search() got an unexpected keyword argument 'query'"). Server injects its own schema (delegate: reason; web_search: objective + queries) and the model adds those args even when not declared. Both models.
- Server tools auto-chain: after a server function_call_output the server starts the next response itself (no response.create from us). With a bad kwarg the model self-retries: 1.5 dropped `task` after 2 errors; 1.0 kept sending `task` 5 times and then answered itself. Each retry preambles "One moment."
- web_search still server-side on 1.5 and works (ranked excerpts with URLs ~0.5 s after the call, final answer ~1 s later). 1.5 grounded the answer in the excerpt ($175); 1.0 said "$50 on the official site" (not in the excerpt shown, likely hallucinated) — N=1 each, inconclusive.

## Update after 7 more 1.5 runs (12 total on 1.5, 4 on 1.0)
- 1.5 first-turn outcome, N=12: called delegate_task 6/12, fake claim with no call 4/12 (always "I've handed that off to an agent..."; matches higgslive CLAIM regex, so the NUDGE guard would fire; whether 1.5 then calls is untested), upstream_error 2/12. Excluding errors: 6/10 call, 4/10 fake. 1.0: 4/4 call.
- 1.5 reliability: 8 of 42 responses failed with `server_error/upstream_error` "an upstream service call did not complete" (response.done status "failed"), at any position (T0, ack, turn, recall), with 1 or 4 sessions in parallel. 1.0: 0/24. (Other testers were also hitting 1.5 at the time.)
- Q2 on 1.5, N=6 calls: natural ack 3/6, upstream_error 3/6; never a re-greeting. When the ack failed, 1.5 mentioned the handoff in the next unrelated answer ("I've handed off the file creation. The capital of Australia is Canberra.") 2/3.
- Q1 on 1.5, N=6: open call survives 2 unrelated turns, no re-call, no call-related error. Q3 on 1.5: output at 30 s incorporated 6/6, recalled 4/6 (other 2 = upstream_error).
- Layer impact: (a) 1.5 speaks a preamble with the call AND the layer's bare response.create then gets a second ack: two back-to-back utterances on 1.5 ("I'll get that set up..." + "I've handed that off..."). (b) 1.0 multi-call (2/4 runs, up to 4 calls for one request) → layer emits one session.delegation.created per call → the bridge would spawn several agent jobs for one request. This contradicts the 3/3 clean result in IDEAS.md and affects the current 1.0 demo.

N=5 per cell of tools {0,1} × MECHANICS {0,1}, then N=3 sequential on key 1 and N=3 on key 2: same bands in every cell. Ablation N=3 each (tools/tool_choice/temperature present or absent, temperature 0.5/0.8/1.0, a bare session): a bare session still gave 1.5 s twice and failed once. Error rate with 3 sessions in parallel ≈ 50%; sequential 0/24.
- P2.2 parallel calls on 1.0, N=12 per arm, same request: shipped TOOL_DEF gave >1 delegate_task in 9/12 responses (2 calls ×8, 3 ×1). The description helps but doesn't fix it: the layer should open only the first call per response.
- P2.4 speculative calls (a_spec.py, r.wav: 15.1 s `say` clip, task clear in the first 3 s, server_vad, tools declared, text out), N=3 per model: NO response.*, function_call or transcription event before speech_stopped on either model. So the layer can't start the agent early from server events; the earliest signal is the call itself.
- P2.4 timing speech_stopped → call args done: 1.5 0.55 s (3/3); 1.0 0.85-1.0 s. Args arrive as ONE delta holding the full JSON on both.
- P2.4 1.0 double-calls from audio too: 3/3 responses carried 2 delegate_task calls (paraphrased duplicates). 1.5: 1 call + spoken preamble ("I'll get that file set up for you right away.") 3/3, no fake claim from audio 3/3, 0 errors (sequential).
- P2.5 two calls in flight, outputs returned in reverse order (count result first, then groceries), N=3 per model sequential: attribution correct and both recalled correctly 3/3 on both. BUT after only the SECOND task's output arrived, the model said the FIRST was done too: 1.5 2/3 ("the groceries.txt file should be ready as well" / "is ready too"), 1.0 1/3 ("groceries.txt has been created ... and there are 47 Python files"). A pending task gets reported as done when a sibling result lands. Barge-in with a pending call: NOT TESTED (time).
- 1.5 task text is more specific than 1.0's ("in the current working directory", "files with the .py extension ... report the total number") 3/3.
- P2.1 RERUN with one reply at a time per key (C found 1.5 allows ~2 concurrent replies per key; the earlier errors were collisions). Base on key 1, strong on key 2, N=24 each, 0 upstream_error: base 17 call / 7 fake (29%); strong 19 call / 5 fake (21%). Strong line is not a reliable fix (difference within noise at N=24).
- NUDGE on 1.5 (sent exactly as _handle does), N=12 (7 base + 5 strong): 12/12 called delegate_task with a correct task. The guard works on 1.5 once it fires.

It misses "I've handed that task off...", "I've handed off the task...", "I'm handing off the request..." because it requires `hand(ing|ed) (that|it|this) off`. A looser pattern like `\bhand(ing|ed)\b[^.]{0,20}\boff\b` covers all 15 (suggestion, not applied).
- Phase 2 error counts (P2.1 first run, 50% errors) were collisions, not model behaviour; P2.2-P2.5 ran with 0 errors except as noted.

## Phase 3: pending call vs barge-in (a_barge.py; test p3-barge; 1.0 on key 1, 1.5 on key 2, one reply at a time, 0 upstream_error)
Sequence: spoken task (t.wav, `say`) → call → bare ack → q.wav (Ottawa question) streamed from the ack's first audio delta → auto reply → text turn → item.retrieve ×2 → function_call_output at 30 s → bare response.create → recall turn. N=3 per model.
- Barge-in cancels the ack: response.done status "cancelled" (status_details null) 3/3 on both, at the same instant as speech_started (0.2-0.25 s after the ack's first audio delta). The pending call is untouched: no error, no cancel and no event of any kind referencing the call_id, 3/3 on both.
- conversation.item.retrieve on the function_call item, after the barge-in and again just before the output: status "completed", call_id matches, 6/6 per model. "completed" means the call item finished generating, NOT that it got an output: no item status shows a call is still pending; the layer must keep track itself (it does, `_open`).
- function_call_output at 30 s: conversation.item.added 3/3 on both; the next bare response reported the result 3/3; recalled correctly on a later turn 3/3 (1.5 quoted the exact date 3/3; 1.0 said "today's date" 2/3 then gave it on recall).
- The Ottawa answer after the barge-in and the unrelated text turn: normal, no re-call, no premature result, 3/3 both.
- 1.0 double-called again from audio 3/3 (one an exact duplicate, one an extra "open the notes file" step); only the first call was answered and the extra stayed open with no error.
